# 图片转拼豆 · 算法对比基准

用来验证「色号匹配 / 背景估计 / 抖动」三类改动的**质量与耗时**，改造前后同参数对比、可复跑。
纯 Node 脚本，零依赖；不参与前端打包，也不会被 Service Worker 缓存。

## 怎么跑

```bash
node bench/run.mjs          # 主基准：9 张固定图 × 卡通/写实 × 旧版/新版，写入 bench/results/latest.json
node bench/visual-report.mjs before            # 观感/边缘专项：9 图 + 熊图，原图|结果 对比图 + visual-before.json
node bench/visual-report.mjs --combine before after  # 输出「原图 | 改前 | 改后」三联图
node bench/color-mismatch.mjs [width] [colors] [style]  # 逐格找「豆色和原图对不上」的格子，区分色板下限与算法选错
node bench/edge-report.mjs now                 # 边缘专项：去背景模式「原图 | 旧版 | 新版」+ edge-now.json
node bench/aspect-check.mjs                    # 长宽比例：5 种比例 × 3 种宽度 × 2 种色数，断言不通过会退出码 1
node bench/bear-diagnose.mjs [before|after]     # 真实照片回归样本：加 tag 输出两套图，便于前后对比
node bench/match-bench.mjs  # 色号匹配：真实色板命中率与耗时
node bench/anime-bench.mjs  # 二次元专项：平涂纯度 / 描边保留 / 高光保留（支持 WIDTH/COLORS/BG 环境变量）
node bench/gen-bluenoise.mjs # 重新生成 js/bluenoise.js（蓝噪声阈值矩阵，结果确定）
```

`bench/legacy-convert.js` 是改造前 `js/convert.js` 的冻结副本（只改了 import 路径），
**不要修改**，否则基线失效。`bench/png.mjs` 是零依赖 PNG 读写，给 Node 侧读图/写对比图用。
`visual-report.mjs` 的 `before` tag 固定走这个冻结副本，`after`/其它 tag 走当前版本——
否则「改前」只是把现在的图再输出一遍，对比没有意义。

## 指标（bench/metrics.mjs）

| 指标 | 定义 |
| --- | --- |
| ΔE00 均值 / 截尾均值 / p95 / 最大 | 每格「原图 5×5 子采样平均色」与最终色号之间的 CIEDE2000；截尾均值去掉最差 5% |
| 孤立豆比例 | 四邻域中没有同色邻居的格子占已用格子的比例 |
| 明度偏差 | 原图与结果按 L\* 16 档直方图的 L1 距离（0 最好） |
| 黑白偏差 | 深色（L\*<20）与浅色（L\*>85）占比之差的和 |
| 边缘保持 | 原图 Sobel 边缘有多少能在结果里（允许 1 格偏移）找到——召回率；抖动多出来的边缘不算丢失 |
| 平滑台阶/千 | 只统计源图相邻参考色每通道差 ≤8 的格子对（人眼期待连续过渡），结果两格色差 >22 记一次台阶，按每千对归一化 |
| 平滑最大台阶 | 上述平滑对里最大的结果色差，用来抓个别突兀的硬边 |
| 细线断裂率 | 格内深色像素 ≥6% 且浅底 ≥40% 的细线格，结果在同位或沿线方向（不跨线）找不到 L\*<65 的深色豆即算断 |
| 细线同位率 | 更严格的版本：只认同一格是否保留深色豆，用来观察边缘采样有没有把细线稀释成浅灰 |
| 分阶段耗时 | 采样 / 目标色 / 排序 / 选色 / 上色 / 清理（`options.timings`，不传则零开销） |
| 同格 ΔE00 | 只比较新旧两版都保留的格子，排除「背景去除范围不同」对 ΔE 统计的干扰 |

二次元专项（`bench/anime-bench.mjs`，只跑 `animeFixtures`，不参与上面的历史基线）：

| 指标 | 定义 |
| --- | --- |
| 平涂纯度 | 格内最大偏差 <8 的平涂格，比较参考色与最终色号的 ΔE00；「色板下限」是整块色板里最近色的 ΔE，「可避免%」是「ΔE>6 且色板下限 ≤5」的占比（算法选错的份额） |
| 描边保留 | 同格深色占比 >15% 且浅色 >20% 的描边格，3×3 邻域内有 L\*<62 的深色豆即算保住（允许 1 格偏移） |
| 描边同位 | 更严格：只认同一格有没有排深色豆，用来观察 1 格宽的轮廓是否被稀释成浅色 |
| 高光保留 | 排除背景格后，深色 >40% + 浅色 >15% + 最亮 >95 的高光格，3×3 内是否有 L\*>58 的亮豆 |
| 浅格误黑 | 参考格亮（L\*>82）且几乎不含暗像素（深色占比 <5%），结果却排了 L\*<50 的深色豆——算法凭空发明的黑豆。只有「不足 1 格宽的描边落在亮格里」不算 |
| 孤立豆 / 细线断% | 与主基准同定义，用来确认二次元专项改动没有破坏通用指标 |

### 豆色和原图对不上：目标色统一 + 大块暗区边界不升格

用户反馈「对比原图时有些豆的颜色和图上的对不上」。用 `bench/color-mismatch.mjs` 逐格把
「原图 5×5 平均色」与最终色号做 CIEDE2000，并减去「整块色板里最近色」的下限，定位到两类
**算法选错**（不是色板不够）：

1. **同一格两套颜色判断**：目标色（选色直方图用）认定「暗部占主导」给出深色，最终上色却
   再按逐像素匹配做多数票；深色被拆成几个相近色号、都没过半，于是回退到整格的线性平均色，
   结果眼睛/暗块里冒出一颗浅色豆（`portrait` 实拍 6.68→4.98）。
   现在最终上色直接用 `targetGrid`（`chooseCellColor(target, matcher)`），顺带省掉每格 25~49
   次逐像素匹配，110 格单张耗时 749→428ms（保留背景口径）。
2. **暗色小特征被整格升格**：`minorityDarkFeatureRgb` 本来是为白底细线/眼睛设计的，只要格子
   整体偏亮、暗像素≥10%~15% 就整格上暗色。物体边界（头发、深衣、深色背景压到格子边缘）因此
   被整格涂成近黑，对照原图就是「米白/肤色格子里冒黑豆」。新增 `markDarkMassCells`：
   先把暗格（暗占比≥50%）做连通分量，分量里存在 4 邻域全暗的格子（厚度≥3 格）才判为
   「厚实暗区」；只有「某侧边缘暗≥40% 且邻格属于厚实暗区」的格子取消升格。细线厚度只有
   1~2 格，凑不出内部格，不受伤。只作用于「保留背景」模式，去背景模式仍靠 `deepFeatureRgb`
   的全像素扫描保护描边。

保留背景口径（默认）9 图平均：

| 参数 | ΔE00 | 孤立豆 | 细线断% | 平滑台阶/千 | 单张耗时 |
| --- | --- | --- | --- | --- | --- |
| 110/40 改前 | 5.06 | 0.98% | 1.75 | 32.08 | 749ms |
| 110/40 改后 | 4.88 | 0.90% | 4.60 | 31.40 | 430ms |

48 格 / 16 色请直接看下面「二次元专项」的 48 格表和 `visual-report.mjs`，两组不再混在一起记。

细线断裂率上升**不是把真细线抹掉了**：该指标把「深色像素≥6% 的浅色格」一律算细线，
照片里主体边缘的抗锯齿格全在统计内，而这次改动正是要让这些「大部分是浅色」的格子
按浅色排珠。真正的线稿 `lineart` 反而从 9.4% 降到 0.2%（110/40），`logo` 保持 0%；
`photo-bear` 的黑色描边在 110/40 下仍然连续，只是少了一圈“加粗”。残留的大误差集中在
「2 格厚的暗带压边」——与 2 格厚的描边在像素层面无法区分，属于有意的取舍。

同格 ΔE00（都保留的格子）新旧基本持平（多数 ≤0.25，`photo-mix` 6.79→7.02、
`photo-bear` 4.63→4.86），说明量化精度没有退化；主体 ΔE 的改善来自背景去除更准
（残留背景格不再参与统计），以及两段式色号匹配（top-32）减少了偏色。

### 真实照片：写实模式默认清理 + 确定性 + 背景置信度

三处针对性改动（都在 `js/convert.js` / `js/color-match.js`，不动 `legacy-convert.js`）：

1. **写实模式默认不清理**：`postStrengthBias` 由 `-1` 改为 `0`。之前写实模式
   `speckleStrength = clampStrength(1 - 1) = 0`，后处理整段空转，噪点图里成片的单颗抖动豆
   被当成「细节」保留。改后默认走 1 级清理（只合并真正孤立/微小的同色块）：
   写实孤立豆 16.00%→6.76%、平滑台阶 350→220、主体 ΔE 5.22→5.29 基本持平、细线断 17.41→9.06。
2. **确定性**：`getMatcher` 会按色板数组缓存 matcher，而 matcher 内部有 5bit/通道的匹配缓存。
   整块色板的 matcher 跨图片复用这个量化缓存，等于让「先转换的那张图」决定同一色桶的答案——
   同一张图先转/后转结果不同（实测 `logo` 110/40：先转 ΔE 8.01 / 后转 8.11，色数 5 vs 6）。
   现在每次转换用 `createMatcher(activePalette)` 建独立实例；色板预计算仍然复用，只有匹配
   缓存按图片隔离。`match-bench` 命中率不变（MARD 99.98/100/99.95，ARTKAL 99.98/99.83/100/100）。
3. **每格背景色只统计高置信度像素**：掩膜向外扩的 1 像素（主体交界混色，置信度 ≤0.35）会被
   计入「本格背景色」，把背景色估成肤色/主体色。之后 `scanCellDarkFeature` 看到「浅色背景」
   就启动全像素找暗线，结果把真正的深色背景当成描边，整格涂成黑豆——`dark-bg` 31% 的
   主体边缘格中招（参考色 194,176,155，输出 H6 47,43,47）。改为只累计置信度 >0.35 的像素后：
   `dark-bg` 边缘染色 31%→0%、ΔE 4.11→3.59、孤立豆 4.6%→0.6%；`lineart` ΔE 36.73→37.48 略升
   但细线断 4.9%→0.2%（保留更多线格）、`photo-mix` 6.88→6.78。
4. **1 级清理走快路径**（`reduceTinyRegions`）：1 级只处理「一格宽」的孤立块，逐格查四邻域即可，
   不需要为每格开 BFS 队列和 Map。输出与 BFS 版逐格一致，去掉的只是分配开销；实测写实模式
   110/40 单张 287→265ms，卡通 459ms，相对冻结基线仍是 1.0~1.1×。

被评估后**撤销**的两个方案（指标不达标，不要重试）：

| 方案 | 结果 | 撤销原因 |
| --- | --- | --- |
| 邻格暗占比≥0.5 时禁止暗色升格 | 照片 ΔE 明显下降（portrait 5.41→5.12、photo-bear 7.25→5.87） | 细线断 6.34%→22.79%，粗描边被削细（lineart 0.2%→17.9%），违反「不破坏细线」 |
| `darkMass` 为真时一律禁止方向性升格 | 保留背景 ΔE 4.91→4.86 | 细线断 1.22%→5.04%（dark-bg 2.6→17.4、photo-mix 2.3→15.9），得不偿失 |

`dark-bg` 的「细线断%」在这次改动后从 72% 升到 81%：该指标把「深色像素≥6% 的浅色格」
一律算细线，而 dark-bg 的深色像素就是背景本身，指标要求在那里继续排黑豆——
正好是要修的黑豆缺陷（`legacy-convert.js` 在同一张图上是 100%）。照片/线稿两类真实
场景的细线断都是下降的。

- 粗筛保留 32 个候选：16 个时近似照片色会漏 1.4%，最大多付 ΔE00≈5（肉眼可见的偏色），
  32 个把代价压到 0.06；粗筛本身就是一次全量扫描，所以耗时几乎不变。

## 背景估计：四角采样 + 连通性 + 膨胀

修复「浅蓝天空被当成主体、描边混出脏色」时定下的做法（`js/convert.js`）：

1. **四角采样**：取四个角各 14% 边长的小块（约 12×12 点）做 k-means(≤4)，只接受至少覆盖
   2 个角的簇作为背景色。这样满幅渐变、主体偏一侧的图不会被整幅当成背景。
2. **渐变用中间色补**，而不是放大容差：相邻背景簇之间距离在 50~260 时插一个中间色中心。
   容差一旦放大（曾放到 59.5），米白身体 [233,232,227] 距浅蓝中心仅 58 就会被一起吃掉。
3. **连通性约束**：从画面四边做 BFS（4 邻域）洪水填充，只有和边缘连通的背景像素才算背景，
   主体内部同色区域不会被挖空。
4. **1 像素膨胀**：描边与天空的抗锯齿过渡色既不算背景也不算深色特征，会残留一圈淡蓝脏色；
   背景遮罩膨胀 1 像素后这圈被吃掉（局部分阶段 +~27ms @1236²）。
5. **边界格清理**：格子背景占比 ≥50% 且没有深色描边特征时留空；有深色特征则保留，避免把描边削断。
6. 四角方案不成立时（角落颜色不统一）回退到旧的边界采样 + Otsu 路径。

## 观感专项：平滑区色阶台阶

目标：减少天空/皮肤/渐变里肉眼可见的色阶台阶，**不能靠抖动**（上一轮实测「只对渐变区抖动」会把
相邻格跳变从源图 1.8 放大到 22，还多出散点，已回退）。

做法（`js/convert.js`）：

1. **平滑格识别**：格内采样色跨度 <24 记为平滑格；目标色直方图额外记 `smoothWeight`（面积），
   选色时只给「面积 × 跨度」大的平滑区补色，不被碎纹理抢预算。
2. **渐变预算再平衡**：名额用满后做最多 6 次交换——用色板里能填进最大平滑间隙（CIE76 >10）的
   色号，换掉贡献最小的色号；约束是全图加权色差最多变差 1%，且「换掉后某色块没有替代色」的
   关键色不参与交换。候选池用整块色板，避免过渡色因为「没赢过任何像素」而进不来。
3. **平滑区一致性**：只在不抖动时，把「8 邻域里 ≥5 格已是某色、且该色与最近色相差 ≤5 CIE76」的
   平格吸附过去，消除噪声造成的块状色斑；贴着非平滑格（描边/细节）的格子不动。
4. 试过并否决：对平滑区目标色做 3×3 均值/模糊——`portrait` 台阶 24.4→26.3、ΔE 5.82→6.08，
   属于用糊换平，已回退。

## 边缘专项：细线保护（去背景模式）

保留背景时采样已经是「按格内样本投票取主导色 + 少数深色特征优先」，`lineart` 细线同位率 79.2%、
断裂率 9.4%，边缘召回 1.000，不需要再改。真正会断线的是**去背景**：白底被从样本里剔除后，
一条 2px 的黑线在 110 格下只占格子 5%~30%，7×7/11×11 点采样经常整格落空，结果就是线断成点。

做法（`js/convert.js`，只影响 `backgroundMode='remove-white'`）：

1. **整格暗特征扫描 `scanCellDarkFeature`**：对每个“被剔除过背景”的格子，按全部像素统计
   “比背景暗 70 以上、且接近中性灰”的像素占比；占比 4%~50% 判定为细线/细描边，
   取其中 `L*` 更暗的线芯均值作为该格颜色。深色底不做（`背景亮度 < 150` 直接跳过）。
   高饱和平涂色（logo 的红/蓝）不算暗特征，否则边界格会把主体撑胖一圈。
2. **特征格按边缘格保护**：`edge` 标记带上深色特征，`reduceSpeckles`/`reduceTinyRegions`
   不会把保留下来的单颗线芯当成孤立豆删掉。
3. **选色/目标色把线芯算进去**：`rankPaletteColors` 与目标色直方图对特征格直接计线芯颜色，
   避免黑色/深灰因为“样本太少”进不了候选色。
4. **否决 11×11 补采**：边缘格用更大采样面会让平均色被更多浅底样本稀释，细线更浅，
   实测 `portrait` 细线断 0.8%→3.3%、`photo-mix` 2.3%→6.8%，已移除。
5. **否决保留背景也走整格扫描**：浅底平格里会把抗锯齿过渡当线，`lineart` 台阶 0.6→2.3/千、
   `portrait` 11.1→12.0/千，属于过度锐化，已移除。

## 二次元专项：描边连续性 + 眼白高光

用户的实际素材以二次元图为主（平涂 + 硬边描边 + 大眼高光），所以单独建了 fixture 与指标
（`bench/anime-fixtures.mjs` / `bench/anime-bench.mjs`），并在卡通模式下做了三处改动。

### 问题

用 `anime-bench` 把 110 格 / 40 色 / 卡通跑出来，两个肉眼可见的缺陷：

1. **轮廓断成虚线**：二次元的描边通常只有 1~3px，在 1 格 = 4.65px 时不足 1 格宽。抗锯齿把
   同一条线切成「深一浅一」的格子，只有暗像素够多的格升格成暗色豆，于是脸/头发的轮廓
   一串黑豆隔一格断一次。
2. **眼白/高光被虹膜吃成黑豆**：`directionalDarkFeatureRgb` 只要「整格偏亮 + 暗像素 ≥8%」
   就整格升格，虹膜压在眼白/高光边上正好满足条件。保留背景时更糟：白底本身被
   `minorityLightFeatureRgb` 当成「亮点」，本该是描边的格子被排成白色，反向挖出一串洞。

### 改动（`js/convert.js`，均只影响卡通模式）

1. **大块暗区压边不升格**（`markDarkThicknessCells` + `thickMassFringe`）：先标出「四邻全暗」
   的内部格，再对被升格候选格逐侧检查——每条暗像素占比 ≥40% 的边向外看两格，碰到内部格
   说明那一侧是头发/虹膜这类厚度 ≥3 格的大块暗区，这一格只是被啃到的浅色边界，不整格升格；
   两条相邻边都暗 ≥40% 时再检查对角方向（斜角楔形压进来的暗区）。细线只有 1~2 格厚，
   永远凑不出内部格，因此不受影响。
   卡通模式用它取代粗粒度的 `darkMass` 判据：48 格宽下描边只有 0.3 格厚、又常紧贴头发，
   `darkMass` 会把整段轮廓排成背景色；`thickMassFringe` 只在真有大块暗区时拦截。
   写实模式仍用 `darkMass`：照片的噪点/边缘本来就大量贴在大块暗区上，收紧后细线断
   9.06%→9.31%，观感收益也不明显。
2. **亮特征只在去背景模式启用**：保留背景时背景像素没有从样本里剔除，白底与白色高光是
   同一个颜色，无法在格内区分「高光」还是「白底」，这条通路会把轮廓格排成白色。
3. **补齐细线断点**（`fillLineGaps`）：对「自己是浅色格、含少量暗像素、左右/上下/对角线两端
   都是浅色格升格出来的细线」的格子，直接沿用两端更暗的线色。只补单格断点，且两端都要求
   是细线（大块暗区边界不参与），所以不会把暗区补胖。

  背景像素，兜底分支几乎不触发，已撤销。
- **平涂色额度保底**：三个配置下平涂「可避免」只有 0.0%~0.4%，平涂 ΔE 已经贴着色板下限，
  再追加额度只会挤掉别的颜色，不再新增。

## 长宽比例专项

用户反馈「生成结果长宽不一致」。实测结论：**转换算法本身没有问题**——源比例到网格高度按
`round(源高/源宽 × 设定宽度)` 换算，`viewer` 取景、裁剪、Worker 回传也都等比；不一致来自展示和导出两处：

1. **缩略图被裁成方形**：`.project-thumb` 是 64×64 + `object-fit: cover`，竖图/横图只显示中间一块，
   卡片上的长宽比和图纸对不上。改为 `contain`：完整显示、两侧留白。
2. **导出画布宽高分别截断**：`export.js` 原来对 `canvas.width/height` 各自 `Math.min(12000, …)`，
   超高图（110×587）底部约 1124px 连同整个图例被裁掉；而且没有面积上限，iOS Safari 超过约
   16.7M 像素会导出空白图。改为 `chartLayout()` 先算布局，再用**同一个缩放因子**同时收缩格子
   （`MAX_SIDE=12000`、`MAX_AREA=16M`），宽高比严格不变。
3. **高度取整**是唯一剩下的误差：`round()` 最多差 0.5 格，属于像素网格的必然结果，不是拉伸。

自动化断言 `node bench/aspect-check.mjs`（5 种比例 × 宽度 16/48/110 × 16/40 色，共 62 项全过）：
网格行列 = `round(源高/源宽 × 宽度)` 且误差 ≤1 格；`computeFit` 单一 scale 且居中；`thumbSize`
比例误差 <1px；`chartLayout` 两轴同格、画布不超限；CSS 缩略图 `contain`、打印格子宽高同取 `--cell`。

| 正方形 | 600×600 | 110×110 | 2492×2630 | 22.00×22.00 |
| 竖图 | 600×900 | 110×165 | 2492×3866 | 22.00×22.00 |

## 已知取舍

- **满幅渐变图仍可能被当成背景**：这类图四角颜色各不相同，通常会走回退路径；`gradient` 图
  现在保留 9853/10399 格（旧版 10361），损失主要来自边缘一圈。观感不对时建议手动关掉「去背景」。
- **纯色/浅色/打光渐变背景收益明显**：`portrait`、`product`、`photo-mix`、`photo-bear` 都少了一整圈
  残留背景。
- **抖动可切换**：`options.ditherMode` 支持 `'blue-noise'`（写实默认）、`'error-diffusion'`（旧行为）、
  `'none'`。若某类图蓝噪声观感变差，可在调用侧切回 `'error-diffusion'` 复现旧效果。
- **边缘召回不惩罚抖动**：蓝噪声会在主体边缘外再抖出一圈边缘，Jaccard 会把这部分算成「并集变大、
  召回变低」，所以改成召回率并允许 1 格偏移，只关心主体边缘有没有丢。
- 大图（1236²）110 格卡通约 0.75~0.85s（桌面 Node；平滑格目标色直接用格内平均后省掉了逐格聚类，
  目标色阶段 410ms→30ms），背景遮罩新增约 75~100ms。
- **软边缘会被压平**：平滑区一致性会削掉柔和渐变的 Sobel 梯度，`portrait` 边缘召回 0.978→0.966；
  这是「减少可察觉色阶」的代价，硬边/细线不受影响（lineart、product 边缘仍为 1.000）。
